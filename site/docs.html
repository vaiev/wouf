WOUF guide

Overview

A sandbox is a separate workspace that limits what a bot can access. Host mode has no sandbox. Headless means the bot runs the assistant without an interactive chat window.

What WOUF is

WOUF is an agent team in a folder, set up with the AI tool you already use. You talk to one lead. The lead hands tasks to a worker, has a reviewer check the result, asks a decider for the hard calls and tells you what happened.

It is not a product or a platform, and it does not replace your agent CLI. It is a folder of plain instructions plus small helper scripts written in standard-library Python. You copy that folder into a project and keep using your own agent CLI, such as Claude Code, Codex CLI or another CLI that reads AGENTS.md.

WOUF is only the example name. You can call your team whatever you like.

Just get startedUnderstand and adapt

A plain folder

Everything lives in one folder, .agents/, next to your work:

  • the rules every member follows, in .agents/rules.md

  • the roles: lead, worker, review, decide and specialist, in .agents/roles/

  • the skills the lead loads for a step, such as writing a brief or reviewing and merging, in .agents/skills/

  • your own team: settings, bots, board, decisions, schedule, knowledge and logs, in .agents/team/

  • small helper scripts in .agents/bin/, mainly team for bots, runs and checks, log for receipts and search, and secret for keys

The board, the decisions, the schedule and the knowledge are files you can open and read. An update replaces the shared pack and leaves .agents/team/ as it is.

A team that works by a method

What makes the folder a team is the method, not a new program:

  • you talk to one lead, and the lead does not do the work itself

  • every piece of work starts from a written brief

  • a second bot reviews the result in a fresh context

  • hard calls go to a decide bot or to you

  • anything irreversible, outward, paid or needing new access waits for your yes

The method part of this guide explains each step.

Where the safety comes from

The rules are instructions to the models. A model can still get them wrong. Docker, Podman and bubblewrap runs stage inputs and a repository copy into a separate workspace; host mode runs without a sandbox and can access the host under the user's permissions. Results come back only as plain files.

The safety part of this guide explains the sandbox modes and their trade-offs, and the limits part says plainly what WOUF does not do.

Try it without a model

.agents/bin/team demo runs an offline demonstration with a fake agent. It shows the gate that checks a change without any model, and an approval that only counts for the exact commit it names. It needs Python 3.9 or newer and git.

Method

WOUF works the way a small company works with a team. This part explains who does what, and which steps are checked by code and which are rules the models are asked to follow.

One lead

You talk to one member only: the lead, called WOUF unless you rename the team. The lead is the agent CLI session you already use, started in your project folder.

The lead talks to you, writes briefs, hands them out, relays questions and reports back. It does not do the work, review it or decide alone. Bots never talk to you directly; they ask the lead, for example "WOUF, I need the logo file from the user", and the lead collects such questions and asks you once.

This is a rule the models are asked to follow, not something a program can force on a model.

Roles

Each member has one role, written down in .agents/roles/:

  • Lead: talks to you, briefs, dispatches and reports.

  • Worker: does the briefed work, and only that, in its own sandbox.

  • Review: checks one result against its brief and approves or asks for changes. It never fixes what it reviews.

  • Decide: makes a hard call once, with reasons, when the brief and the rules do not settle it.

  • Specialist: a bot for one domain, such as the example research, writer, tester and ops bots.

Nobody grades their own work. Flows also use helper bots: a scout that reads the code first, a bugfixer, and a planner that turns a large goal into a plan and draft tasks for the lead to read.

The brief

Every piece of work starts from a brief. A brief states the objective, the acceptance criteria, the paths the work may touch, what is in and out of scope, the inputs and the expected output. team brief new prints an empty brief with the next free task id.

The brief's Class: line picks the bot, the tier and the number of reviews: for example mechanical runs on the light tier with one review, and security runs on the strong tier with two reviews.

The brief's Paths: line is checked by code. Before any review, a pre-gate without any model checks the branch: a changed file outside those paths turns the gate red, and so do failing tests when you configured a gate command. The gate command gets no keys. In container and bwrap mode it runs in a sandbox; in host mode it runs in a throwaway clone on your computer, with no sandbox. A red gate sends the work back to the worker once; a second red gate blocks the task.

Fresh, independent review

A second bot checks every result, in a fresh context and its own sandbox, so it does not inherit the worker's reasoning. It checks the result against the brief, not against the worker's summary.

The review role asks an approval to name the exact commit it checked. team flow accepts an approval only when the commit it names is the head of the task branch. It accepts the full commit id or a shortened one of at least 7 characters that the head's id starts with, as git shows short ids. An approval of another commit, a commit id shorter than 7 characters or a missing commit counts as no approval. Any new commit needs a new review.

Decide

Some questions do not follow from the brief and the rules: two reasonable options, rules in conflict, or high risk. The lead then asks the decide bot, which picks one option, names the remaining risk and hands the decision back.

How far the team may decide without you is a setting, autonomy in .agents/team/config.ini:

  • ask, the default: decisions go to you.

  • auto: the lead decides reversible things inside the rules with the decide bot, records them in team/decisions.md and tells you in its next report.

In both settings some things always wait for your yes: sending, publishing, deploying, purchasing, deleting or overwriting outside a sandbox, merging to main, new access such as a new key or host, and anything that costs money. These limits are rules for the models. Merging and publishing are your own steps.

Speak up

Every member says so, unasked, when something is wrong, missing, risky or could be better: bots under Flags in their return block, the lead to you.

A whole task on its own

team flow <task> takes a brief through worker, pre-gate, review and up to two rounds of rework. It ends ready with an approval on the exact head, blocked, limited or with one question for you. If a run hits a usage limit, the flow waits, or switches once to another CLI when you configured a fallback.

A goal too big for one brief goes through four phases: INIT, CONCEPT, REALIZE and VERIFY. Leaving a phase needs an explicit yes, and with autonomy = ask your yes first.

Safety

The rules in .agents/ are instructions to the models. A model can misread or ignore them. What actually limits a bot is the place it runs in, the network it gets and what comes back from it. This part explains each, with its trade-offs.

How .agents/ is built

  • .agents/rules.md, .agents/roles/ and .agents/skills/ are the shared pack: plain text every member reads.

  • .agents/team/ is your team: config.ini with the settings, bots/ with your bots, and the board, decisions, schedule, knowledge and logs.

  • .agents/bin/ holds the helpers. They are standard-library Python, so the pack needs no package installs of its own.

  • .agents/bots/ and .agents/connectors/ hold examples. They are off until you say yes, and a connector reaches only the bot that lists it.

Setup copies .agents/ into your folder. Outside it, setup only touches your own secret store and installs software you agree to; it changes no global settings.

Sandbox modes

mode in the [environment] section of .agents/team/config.ini says where bots run. A new team starts as undeclared, and the lead runs setup first.

Docker, Podman and bubblewrap runs stage inputs and a repository copy into a separate workspace; host mode runs without a sandbox and can access the host under the user's permissions.

Container (recommended)

One image for the whole team holds the agent CLIs and tools. Each bot has its own storage, and its container exists only while it works on a task. The container gets the bot's storage as its only volume; the original project and home folders are not mounted as such. The lead copies the brief and inputs in and the results out.

Every container the helper creates drops all capabilities, cannot gain new privileges and has a limit on processes; a bot's container also has CPU and memory limits. A bot that works longer than the time limit is stopped.

This needs Docker or Podman, on your computer or on a VM or server reached through an SSH alias.

Bubblewrap (bwrap)

For Linux without Docker or Podman. Each run gets a bubblewrap sandbox with its own namespaces, no capabilities and no host environment variables. It sees its own folders (its storage, inputs and outbox, and a small team prefix that stands in for the image) and, read-only, parts of your computer: the program folders such as /usr, /bin and /lib, and a fixed list of entries in /etc, such as certificates, time zone and name resolution settings. Nothing of your home folder or project is mounted. Anything kept in those program folders or /etc entries is readable by the bot, so keep no secrets there.

The message at every start says "only its own folders"; the read-only program folders and /etc entries above come on top.

It is weaker than a container. There is no system call filter, and the run says so at every start. CPU, memory and process limits depend on your computer: where a systemd user scope works, each run and the gate get the memory and cpus settings and a process limit; where it does not, the run warns that there are no such limits and goes ahead without them. team doctor tells you which case you have. Software that needs administrator rights is not installed for the bots; you install it.

Host (no sandbox)

host runs the bots directly on your computer, in .agents/team/env/<id>/, with the agent CLI's own safe defaults. There is no sandbox. Use it only to try things out.

Network and egress

Technical details

network in the same section decides what a bot can reach in container and bwrap mode. In host mode it fences nothing: there is no sandbox, so a bot uses your computer's network whatever network says, none included.

  • bridge, the default: open internet access, which cloud models need. It is not filtered: a bot can also reach your local network and, on a cloud VM, the provider's metadata service. Block those on the engine's host if that matters.

  • none: no network in container and bwrap mode. This only fits local models inside the container. It does not take the network away in host mode.

  • egress: the bot reaches outside hosts only through a proxy for each run, which lets through only an allowlist; the bot's own loopback is the one exception, see below. In container mode the bot sits on an internal network with no way out, and the proxy sits on both networks. In bwrap mode the bot has no network beyond its own loopback and reaches the proxy through a socket.

With egress, each run gets the base allow list plus the model and login hosts of its own CLI. A brief can add hosts for one task with an Egress: line; a host outside the base list needs the lead's recorded yes for that task first.

There is one exception to "only through the proxy": the bot reaches its own loopback (localhost, 127.0.0.1, ::1) directly, without the proxy. This exception is fixed in code; neither the config nor a brief can widen it. It is the loopback inside the bot's own container or sandbox, not your computer's: in bwrap mode a test checks that the bot cannot reach a service on the host's loopback, though that test runs only where bubblewrap can start a sandbox. Separately, the proxy refuses names that resolve to private, loopback or link-local addresses, so the bot cannot reach those through the proxy either. Older Docker and Podman versions with a known name-resolution leak are refused.

bwrap mode refuses bridge, and host mode refuses egress, because there is no sandbox to fence in.

Keys

.agents/bin/secret keeps keys out of the repository, the chat and the bots' storage. You type a key yourself, in your own terminal, with secret set NAME; it has no command that prints a value back. It uses your system's keychain or Secret Service when available, else a file store with owner-only permissions that it refuses to keep inside a git repository.

A bot gets a key for one run, as a line on its standard input, never in an argument or environment variable of the container command. Keys found in what a bot hands back are masked as ***.

Masking prevents accidents. It is not a barrier against a bot that wants to leak a key it was given. The limits part lists the known gaps.

Bot output is data

What a bot prints and hands back reaches the lead framed as data from the bot, not as instructions, and the lead's role tells it so. Results come back as plain files and folders only: the helper skips and lists links instead of following them.

The lead is still a model reading text a bot wrote. The framing helps; it does not make the lead immune to what it reads.

Privacy and where your data goes

You choose where the team and model run. WOUF does not require its own cloud or server.

  • Cloud model: the agent CLI sends the content it uses to its model provider. An allowed network destination can receive data.
  • Compatible local model: the CLI sends content to the model server you configure. Verify model support, authentication, tool use and network reachability in your chosen environment. Other configured services, including Git hosting and external engines, may still receive data.

Docker, Podman and bubblewrap stage inputs and a repository copy into a separate workspace. Host mode runs under your user permissions without a sandbox. Choose what inputs, keys and connectors to provide.

Read the network settings and their limits; read the limits before using real data.

Getting started

What you need

  • An AI assistant for the terminal, an agent CLI, signed in once.

  • Python 3.9 or newer and git.

  • For the sandboxes: Docker or Podman, on your computer or on a VM or server. On Linux without either, bubblewrap can stand in, with the trade-offs explained in the safety part.

If something is missing, the setup tells you what and why, and installs it with you after you say yes.

Set it up

Never opened a terminal? Here is how.

On a Mac: make the folder in Finder. Open the Terminal app, type cd and a space, drag the folder into the window and press Return.

On Windows 11: open the folder in File Explorer, right-click an empty spot in it and choose “Open in Terminal”.

Now type the name of your assistant, for example claude, and press Enter.

Make a folder for your work, open it in the terminal, start your agent CLI there and paste this sentence:

Set up the agent team from https://github.com/vaiev/wouf/blob/main/INSTALL.md in this folder. I am not technical: explain in plain words and do the steps for me.

The assistant sets up the team in this folder, asks for your choices, then runs its checks.

The agent follows INSTALL.md. It copies .agents/ into the folder without overwriting anything, adds the adapter lines your CLI needs, asks you one round of questions with a recommendation each, creates the bots and runs .agents/bin/team doctor and a smoke test. One step is yours: typing your key into your own terminal, so that no key ends up in a chat.

AGENTS.md and adapters

Technical details

Most agent CLIs read a file called AGENTS.md in the folder they start in. Setup adds one line at its end, or creates the file with it:

This folder runs an agent team. Every agent session reads .agents/START.md first.

Some CLIs read their own file instead, so setup adds a small adapter:

  • Claude Code reads CLAUDE.md: setup creates it with the single line @AGENTS.md, or adds that line, and lets the helpers run without prompts in .claude/settings.json. With your yes it also adds session hooks.

  • Gemini CLI reads GEMINI.md: the same, with the line @AGENTS.md.

  • Codex CLI, Antigravity, Grok Build, Cursor and GitHub Copilot read AGENTS.md directly; nothing more to do.

So setup is a few added lines, not a single line for every CLI.

Runners: which CLI runs the bots

Technical details

The lead is your own session. The bots run a CLI too, headless, and each CLI is described once as a runner: a [runner.<name>] section in .agents/team/config.ini. The shipped runners are claude, codex and agy, plus an empty local section to fill in for a CLI that talks to a local model server.

A runner says how to install the CLI in the team image, how to start it in a container and on your computer, how to pass the model and the reasoning effort, and which environment variables carry its key or that it signs in with a subscription instead.

You can choose the CLI for the whole team, for one bot or for one run: "WOUF, use Codex for the worker." The commands in the shipped runners follow each CLI's documentation; check them against your versions.

Tiers: which model

Technical details

Bots ask for a tier, not a model name:

  • strong: the provider's top model, the default for real work, review and decisions.

  • mid: the provider's middle model, for bounded reading work such as the scout and the bugfixer. A runner without a mid model runs it on strong.

  • light: the provider's small model, for mechanical, frequent work.

Each runner maps the tiers to its own models. An empty entry means the CLI's own default model. A brief can ask for another tier, and team run --model NAME picks an exact model for one run. Review, decisions, plans and complex or security work always stay on strong.

Limits

What WOUF does not do, said plainly. Read this before you give the team real data or real keys.

Rules are instructions, not enforcement

The rules, roles and skills are text the models are asked to follow. A model can misread or ignore them. Only the sandbox, the network setting in container and bwrap mode, what comes back from a bot and the checks in code such as the gate and the exact-head approval are enforced by programs. Merging, publishing and branch protection stay with you and your repository host.

Host mode has no sandbox

mode = host runs the bots directly on your computer, as your user. They can reach whatever your user can reach, including the network: network = none does not take it away in this mode. The gate command also runs on your computer, in a throwaway clone, not in a sandbox. It is meant only for trying things out.

Bubblewrap is weaker than a container

mode = bwrap has no system call filter; the run says so at every start. CPU, memory and process limits apply only where a systemd user scope works on your computer. Without one, a bot can use all of the computer's power, and the run only warns about it. The tests check the command that sets these limits, not that systemd enforces them. Tools that need administrator rights are not installed for the bots.

The default network is open

The default is network = bridge. It is not filtered: a bot can reach the internet, your local network and, on a cloud VM, the provider's metadata service. Block those on the engine's host if that matters, or use network = egress.

With egress:

  • An allowed host can still carry data out, for example a package registry that takes uploads. For encrypted connections the proxy sees only the host name, not what is sent.

  • Keys still reach the bot as with bridge; there is no key proxy yet. The CLI's model API and login hosts must be open.

  • The default host lists for each CLI are unverified until you try them: run the CLI once, read the refused hosts in egress.log, and set the lists to what it really needs.

  • The proxy refuses private and loopback addresses, so it cannot reach a model server on your own computer or in a private network.

  • In container mode it needs Podman with aardvark-dns 1.11.0 or newer, or a Docker version with the fix for a known name-resolution leak; older ones are refused.

Secret masking has gaps

Masking keys in a bot's output prevents accidents. It is not a barrier against a bot that wants to leak a key it was given. Known gaps:

  • binary files are not scanned for key patterns; only registered values are replaced in their bytes

  • a registered value split across lines, or spanning more lines than the stream buffer holds, may pass in streamed output

  • a value containing / is not masked in a path

  • your own files are checked only where they are text

The key store keeps keys out of the repository, the chat and the bots' storage, but a process running as your own user could still read it.

The lead reads what bots write

Bot output reaches the lead framed as data, not instructions. The lead is still a model reading text a bot wrote.

What the tests cover

The container flow is tested with Docker and a stand-in agent CLI. The tests that need a real container engine or a working bubblewrap are skipped on a computer without them, so a green run there proves less. The commands for the real agent CLIs and the example connectors follow their documentation; check them against your versions.
