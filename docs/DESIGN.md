# Design

Why the team is built the way it is.

## 1. A folder, not a platform

Everything lives in the project folder: instructions in Markdown, settings in one INI file, six standard-library Python helpers (`team`, `log`, `secret`, `project`, `federate`, `guard`). The human's own agent CLI is the lead; it enters through `AGENTS.md`, the one convention most CLIs share. Nothing is installed globally: outside the folder there is only the human's per-user secret store (`~/.config/wouf/secrets` or the system keyring, section 6) and any prerequisite the human agrees to install. Setup is a Markdown file (`INSTALL.md`) that the CLI follows, because the team is a way of working, not a program.

## 2. Two places, one boundary

- **The project folder** is where the human starts the CLI. Only the lead works here. It needs full access, because it maintains the team.
- **The bot sandboxes**: one image for the whole team (the agent CLIs and tools, built once and rebuilt only when its recipe changes), one storage volume per bot, and a container only while a bot works on a task. Nothing of the project or the computer is mounted. The lead copies the brief, inputs and a git bundle of the repository in, and copies results, logs and a bundle of the bot's commits out; the commits arrive as branch `<team>/<task>`. Keys go in through the container's standard input for that one run, so they are in neither the image, the storage nor the container's configuration.

A run is supervised by a small process in its own session, so the lead's CLI can stop waiting (its tools have time limits of a few minutes) without stopping the bot: `team run --detach` returns at once and `team result` reports later; a run without `--detach` waits for the same supervisor. The time limit is kept inside the container, so results, logs and commits still come back after it. What comes back is copied as regular files only: a link a bot leaves in its results is skipped, because following it would copy files of the computer the results land on. Only the bot's own receipts come back, and the log reader ignores lines a bot writes in another member's name. Containers run without capabilities and with a process limit. Review and decide read the repository but their commits never come back, and a worker's branch only moves forward. On Windows, run the lead in WSL: detached runs and stopping a host run need a POSIX system.

Every run is a fresh process without resume; what a bot needs of the team's memory is staged as its login. `in/LOGIN.md` (at most 6 000 bytes, masked) holds, in this order: the practice file for the run's runner and tier (`team/practice/<runner>-<tier>.md`, else `<runner>.md`, else the bot's declaration), the brief's path, this task's own history from the store (earlier rounds' verdicts and findings, answers to its questions, the decision records the brief names), the top five knowledge and lesson hits for the brief's objective, and a pointer to `in/CONTEXT_GRAPH.md`, the context graph of the brief's `Paths:` at the run's commit (with `--repo` only, at most 400 lines). A section that does not fit is cut with a marker line: knowledge first, then history, then practice. A container run also gets `/wouf/knowledge.sqlite`, an index of team knowledge and accepted lessons only, so `log ask` works in the sandbox. The boot prompt names the login first. The boundary: history rows match the task exactly and come only from what the lead wrote (its events and the receipts in the team's own logs, never a receipt a bot brought back, which may name any task), the index holds no decisions, proposed lessons, questions, runs or receipts, and the generated login, the index and the staged pack hold nothing of another task's briefs, results or receipts. The repository is not filtered: a `--repo` run gets a git bundle of the run's commit with its history, so whatever that repository tracks (a team folder committed to it, with its events and receipts, for example) is visible to the bot. Stored bot text in the login is framed as quoted data, one line per row.

Why not one sandbox for all bots? Shared installs are what one sandbox would give; the team image gives them too. Separate storage keeps what a worker did from influencing the reviewer, keeps a bot that goes wrong away from the others, and lets the lead reset one bot without touching the rest. Why not one long-running container per bot? Nothing should run while the team is idle; a container per task is also a clean start every time, can run in parallel, and has a time limit.

**Egress (opt in, `[environment] network = egress`, stage 1 of `docs/specs/EGRESS-AND-KEY-PROXY.md`).** With `bridge` a bot reaches every host on the internet; with `egress` each run gets two networks, `wouf-<run>-in` (`--internal`, no gateway) and `wouf-<run>-out`, and a proxy container on both (the egress-proxy tool of the catalog, on the team image, read-only root, no keys). The bot joins only `-in`, gets `HTTPS_PROXY` and `HTTP_PROXY` (and `NO_PROXY=localhost,127.0.0.1,::1`, fixed in code: loopback stays inside the bot's own network namespace and never reaches the proxy), and reaches the proxy by the name `proxy`, nothing else: no other host, no IP address, no DNS answer for an outside name. The proxy lets through `CONNECT` to port 443 and `GET`/`HEAD` to port 80 for the hosts on the run's list, at public addresses only, and logs one line per connection; the log comes back as `egress.log` in the run folder and `team result` shows it, masked. The list of a run is `[egress] allow`, the base of all runs, plus `[egress] needs.<runner>` of that run's runner (else the built-in hosts of its CLI), plus the brief's `Egress:` line for that task; `team run` shows it at start. `[egress] private = host:port` (empty by default) names the loopback or private pairs a run may reach through the proxy, for a model server on the host: a literal address or the container host alias and one port each, refused at start when anything else, passed to the proxy as `--private`, said at start, and the bot's loopback variables unchanged. A brief host outside that list needs a recorded lead decision for the task (`decision.recorded`, title `Egress: <hosts>`, by the lead or the human), else the run is refused before anything starts. `team flow` passes the task's line to every step; review and decide get `allow` and their runner's needs only. The networks and the proxy carry the run's labels and are removed after a normal end, a timeout and a crash; what a killed supervisor leaves is removed by label at the next egress run. Refused: `mode = host` (no container to fence in), Podman without netavark or with aardvark-dns older than 1.11.0, and Docker without the fix for CVE-2024-29018 (older ones forward DNS out of an internal network). The staging stays offline: inputs, the pack and the bundles go through engine copies, not the network.

What egress does not close: an allowed host still carries data (a package registry that takes uploads, a code host that takes a gist), and over `CONNECT` the proxy sees only the host, not the method or path. In stage 1 the keys are still in the bot, as with `bridge` (standard input, one run): a bot can send them to any allowed host, and since there is no key proxy, the model API and the login hosts of its CLI must be on the list (`[egress] needs.<runner>`, added to that runner's runs only; a runner with neither it nor a built-in list says so at start). The key proxy (`:8080`), egress for the gate and egress as the default are later stages.

**Bubblewrap (`[environment] mode = bwrap`, Linux, for people without Docker or Podman).** Each run is a `bwrap` sandbox started as the human's own user, with nothing of their environment (`--clearenv`; it gets `PATH` and, with `egress`, the proxy variables), no capabilities, no controlling terminal, and no new user namespace inside (on bubblewrap 0.8.0 and newer). Mounted: the host's programs (`/usr`, `/bin`, `/sbin`, `/lib*`) and a fixed few files of `/etc` (certificates, the loader's settings, the time zone, `nsswitch.conf` and `hosts`), all read-only; the bot's own `passwd` and `group`; the team prefix at `/opt/wouf` read-only; the bot's storage `env/<member>/box` (readable by the human's user only) as `/bot`, writable; the inputs, the pack and the repository bundle read-only; an outbox and a control folder; a private `/tmp`, a minimal `/dev` and its own `/proc`. Nothing else: not the human's home, not the project folder. Before a run a trial sandbox must start; without bubblewrap or with unprivileged user namespaces turned off the run is refused. Keys go in on the sandbox's standard input only, as in a container run. When bwrap has exited, results come back as regular files only, masked, with only the bot's own receipts. The network is `none` (its own network namespace: loopback only) or `egress`: the proxy (`[egress] proxy`, the same lists as above) runs in a sandbox of its own that shares this computer's network, with no keys, and listens on a socket in the control folder; inside the bot a relay takes `127.0.0.1:3128` to it. `bridge` is refused, because bwrap would share the host's network and loopback with the bot, and with it every local service. **The team prefix** `env/_prefix` stands in for the team image (T-0073): the runners', connectors' and `team/provision.sh` install lines run as the human's user in a build sandbox with the new prefix writable at `/opt/wouf`, reaching the network only through `[egress] proxy` (its `allow` plus the hosts the lines name; no network without it), and the prefix is rebuilt only when its recipe changes. **The gate** (T-0079) runs in a bwrap sandbox too: no keys, no network (`gate_network` other than `none` is refused), a fresh `/bot` with home, checkout and an empty read-only hooks folder, and only a copy of the gate cache writable. Every bwrap run says at start what it lacks.

| Compared with a container | |
|---|---|
| Kept | Its own mount, PID, IPC, UTS and user namespaces; no host home; keys only on standard input; a clean environment; results collected after the sandbox exited |
| Weakened | No syscall filter (no seccomp); CPU, memory and process limits only when a systemd user scope works on this computer (T-0080) |
| Lost | Nothing of the image's root installs: `[environment] setup` and any install line that needs root are skipped and named; the human installs them on this computer |

Why containers and not the CLIs' own sandboxes? Those mostly limit writes and network, not reads of the home directory, and they do not separate bots from each other. Containers do both, are the same on macOS, Linux and Windows (through Docker Desktop, OrbStack, Colima or Podman), and work unchanged on a remote engine (`docker_host = ssh://<alias>`) for a VM or a server. `host` mode is kept only for trying things out.

**Host runs and read-only inputs.** A host-mode run (no container, no bwrap) keeps a planner's or reviewer's `in/` and `repo/` read-only by file modes only. Run as root, those modes do not hold, so the inputs are not protected: use a container or bwrap, or run as a non-root user.

## 3. Roles stay separate

The lead talks and orchestrates; the worker works; the review bot reviews in a fresh context; the decide bot decides. Three more core bots serve `team flow`: the bugfixer fixes the `[bug]` defects of a review (a worker, mid tier), the scout writes the context pack for the worker (read only), and the planner turns a goal larger than one brief into a plan and draft briefs (class `plan`, no commits, nothing dispatched; the lead reads, adjusts and dispatches them). Nobody grades their own work. Bots never talk to the human, so the human hears one voice and gets questions in one batch. Bots are expected to speak up about risks, gaps and better ways; with `autonomy = auto` the lead settles those with the decide bot, inside hard limits that always need the human.

A bot declaration may set `until: YYYY-MM-DD` as its last active day; status and runs warn three days ahead, and the bot is excluded after that date.

## 4. Any agent CLI, three tiers

`config.ini` names the CLIs (Claude Code, Codex CLI, Antigravity CLI, a local-model CLI), how to install them in a sandbox, how to run them headless, and the model per tier. `[team] runner` names the CLI; with `auto` it is Claude Code when the lead runs in Claude Code (the only session the helpers recognize), else the first configured CLI found on this computer, so setup names it explicitly. Only `[runner.claude]` ships with tier models; the other runners' tier fields are empty, which runs the CLI's own default model on every tier until setup fills them in. `strong` (the provider's top model) is the default for real work, review and decisions. That a tight brief usually finishes on it in one pass, and so costs less than a cheaper model that needs retries and extra review rounds, is the team's working assumption, not a measured result. `mid` (the provider's middle model) is for bounded work that still reads code, the default of the scout and the bugfixer; a runner without a `mid` model runs it on `strong`, and the log says `mid→strong`. `light` is for mechanical, frequent work. In a flow, a worker or bugfixer run that fails or times out goes again on `strong`, and so does the worker after a red gate; the worker that takes a review's CHANGES keeps its class's tier, and the flow is blocked after two review rounds with CHANGES (the lead's `--answer` grants one more). A flow runs every review on `strong`, and `[class.*]` refuses a lower tier for `complex`, `security`, `decision` (decide) and `plan` (the planner). A direct `team run --tier` is not checked against these rules: there they are the lead's policy. The brief, which says to deliver exactly what was asked, saves more than model choice.

*Classes from the config.* The seven built-in classes stay (`CLASSES` in `teamlib/core.py`); every `[class.<name>]` section of `config.ini` whose name is a lowercase letter followed by up to 30 of `a-z`, `0-9` and `-` adds one, in config order (`known_classes`). Every class check (the brief header, `team task new`, `team brief new`, the goal and plan checks, `bin/project`, `bin/federate`) accepts the same list. A new class needs `tier`; it runs on the worker with one review and no scout unless its keys say otherwise, and `[classify] keywords.<name>` lets the classifiers guess it after the built-in rules. `team doctor` names a section outside the pattern, which no check reads.

*bin/project is a shim over teamlib.* Its class comes from `teamlib.classify` (`class_of`: the same rules, including the security words of `[classify] security_words`, read in the goal and the path names, applied to the paths its own finder names) and its brief check, waves and phase evidence from `teamlib.goal`, so there is one classifier and one brief check. The one classifier never requires fewer reviews than the stricter of the two it replaced: the security words default to bin/project's former stems unless `security_words` is set (with or without `security_globs`) and read the whole goal, while keywords and paths read its first 2000 characters; and bin/project's former stems (`SECURITY_STEMS`, also when `security_words` replaces the default words) and class words (`FORMER_WORDS`) are a floor, so `plan`, `decision` or `analysis` (no review) only where bin/project's words gave a class without review too, else its class (`standard`, `complex`, ...). `tests/test_project_shim.py` holds the table: about 50 goals with main's two classes as literals, checked against `team receipt need`'s review count.

*Steps per class.* A class's flow is a steps table, `preflight* worker [gate review[*N]]` (preflights `scout` and `research`, N 1 to 3): `mechanical` and `standard` `worker gate review`, `complex` `scout worker gate review`, `security` `scout worker gate review*2`, `decision` and `analysis` `worker`, `plan` `scout worker` (`CLASS_DEFAULTS`). `[class.<name>] steps` sets it, e.g. `steps = worker gate review*2`, and wins over the old keys `scout` and `reviews`, which otherwise render into the table; `rounds` (default 2, `FLOW_ROUNDS`) is the number of review rounds with CHANGES before the flow is blocked. `class_options` refuses any other shape, naming `[class.<name>] steps`. `flow_next` walks the table with one transition handler per kind; a preflight runs when it is switched on for the run (scout: the table or the brief's `Scout:` line; research: the brief's `Research: yes` and an active research bot), and a preflight that is not switched on is never scheduled again.

*A run's numbers* (`teamlib/usage.py`). Every boxed run can report its tokens, so the budget (`[budget]`) and `team stats` are not blind for runners other than Claude Code. `[runner.X] usage` says how: `builtin:claude` (shipped for `[runner.claude]`: after the CLI ends, the run script prints one `wouf-usage tokens=in/cache_read/cache_write/out skipped=N` line, read from Claude Code's own session records in the bot's storage), or a shell command the run script runs in the sandbox after the CLI and before the results are copied out, in the task folder, with `$T` and `$USAGE_SINCE` (a file touched when the run began), under `timeout -k 5 60`, its output dropped and its exit status ignored, so it never changes the run's exit code. The bot's own `out/usage.json` is kept: a command that exits 0 replaces it, and a command that fails (or times out) gets it back, so a failed command never costs a valid report. The command writes it, schema `wouf.usage.v1`: `{"schema": "wouf.usage.v1", "tokens": {"input", "cache_read", "cache_write", "output"}}` (each an integer from 0 to 10^12 - 1; no size, count or text limit beyond that), optionally `seconds`, `unknown_runs` and `runs` (per sub-run `role`, `runner`, `tier`, `model`, `tokens`, `seconds`); nothing else. A runner without `usage` behaves as before the key: Claude Code's CLI gets the builtin and every other CLI reports unknown, unless its run leaves an `out/usage.json` itself (an agency writes its own). Any other value (`builtin:nope`, a line break) stops `team run` before its lock. `collect()` takes a valid `out/usage.json` first, for every runner, else the `wouf-usage` line, else unknown, and writes `tokens`, `usage` (the file's object or null), `usage_source` (`file`, `adapter`, `none`) and, for a file that is not the schema, `usage_error` into `result.json`; the receipt's cost stays `tokens=a/b/c/d`, which the budget and `team stats` sum. Host runs report unknown: they would read this computer's own session records.

## 5. Connectors cost nothing until they are used

Example connectors (MCP servers) live in `.agents/connectors/`, one Markdown file each: a usage guide plus one neutral server block. Nothing is installed or loaded until a bot lists one in its declaration. Then what it needs is installed into the team image (or the bwrap prefix), which every bot shares; only that bot's runs get the block translated into the MCP config its CLI reads (its runner's `mcp_arg` or `mcp_path`, e.g. `--mcp-config` for Claude Code), the file as its guide and the connector's keys. This separation holds in the container and bwrap modes; a `host` run's environment also carries every registered value (`WOUF_MASK`, so its own log helper can mask them), so in `host` mode every run can read every key. The shipped Codex, Antigravity and local runners set neither, so connectors are not wired for them (a run says so) until setup fills one in. Keys stay placeholders (`${GITHUB_TOKEN}`) that the CLI fills from the environment of that run.

## 6. Keys are typed once and never stored with the bots

The human stores a key with `.agents/bin/secret set NAME`, which only works in an interactive terminal. On each run the lead passes it to the bot through the container's standard input, as an environment variable of that one run; it is masked in the output and never written into the image, the bot's storage or the container's configuration. A bot can also print a key nobody passed it, and a gate command can too. So every key shape the helpers recognize (one pattern list, the same block in `team` and `log`) is masked as well: in a bot's output, its return block, the gate's output and every receipt, when it is written, brought back or imported, and again before anything is shown or indexed. A private key is masked as a whole block, up to its END line; a block longer than 400 lines is not held but dropped from its header to its END line, so none of its lines is shown. Matches are found in the original text, so a passed value that overlaps a key cannot leave part of it.

**Secrets at the sinks.** Instead of checking each identifier for a key shape, `team` and `log` mask at the places where text leaves them.

*Threat model (binding for the code and for reviews; a review blocks only on findings inside it).* In scope: a registered secret (a value in the secret store, an environment key passed to a run) or secret-shaped content (the key patterns) that a bot wrote (output, return block, result files, receipts) must not appear in stdout, stderr, a traceback, any file `team` or `log` writes, or the SQLite index. Out of scope: names the human chooses (the destination file name of an export, config section names, knowledge file and folder names, symlink targets in the human's own team folder) and metadata derived from them, such as a gzip header; they are not validated one by one. Also out of scope: a value the human types on purpose as a command-line argument or puts in `config.ini` that is neither registered nor key-shaped (a plain `--limit`), and what one gate run can leave for another, which has its own boundary (section 9). Binary files are not out of scope: their bytes are scanned like text (see below).

*What is masked, and where.* One function (`mask_secrets`, the same block in both helpers) replaces every match of the key patterns and the exact registered values with `***`. Registration comes first: at its start `team` registers every stored value (before any argument or the config is read, so a broken config cannot keep a value from the sinks), and `log` reads the same store through the same shared function (`stored_values`) when it starts, then adds the keys `team` passes in `WOUF_MASK`. So a `log` run by hand masks stored values too. Everything written to stdout or stderr goes through one wrapper (`say`, which `die` uses), every text or JSON file through another (`put`, `sink`, `dumps`), and a test reads the code and fails on a direct `print` or write call outside them. Covered: run.json, flow state.json, flow.log, receipts, output.log, briefs, result blocks, and every line `log status`, `task`, `find` and `tail` show; every copy in and out (inputs, the pack, the bot's storage, results, archives) masks its text, and none writes the bot's raw file to this computer first: from a container, collection and archival read the engine's archive as a stream and mask each file in memory before it is written, a hard link gets the masked contents of the file it links to under its own name, and an error half-way (a file that vanished or cannot be read, a failing engine, two names that collide, a link to a file not collected) removes the whole partial copy and is reported in `result.json`; a bot's results in host mode are masked where they stand; each helper has one top-level handler, so an uncaught error is one masked line (`WOUF_DEBUG=1` adds a masked traceback). Every file is scanned as bytes, text or not: a file that is not UTF-8 has its keys and registered values replaced in place, and its other bytes are unchanged; it is listed under `binary` in `result.json`. Registered values are matched across line boundaries too: a bot's output is held back while its last lines may begin a multi-line value, so a value over two lines is masked whole.

*Names.* A copied, staged, collected, exported or imported name is masked per path component, and a changed component keeps a short hash of the original after its first word (`***-1a2b3c4d.md`), so two different secret-shaped names never become one. Before anything is written, staging, collection, export and import check the complete set of masked paths, files and their ancestors: two originals that still land on the same name, or a file that is another member's folder, are refused with a message that shows no value; a refused import leaves no partial files (every destination, in the archive and against the team folder, is checked before the first write). Staging checks the whole input tree before the stage is cleaned, locked or written: two inputs are the same only when they are the same source (their full paths, not their names), so two different folders or files that share a secret-shaped name are refused, never one overwriting the other; and an input cannot take a name the run writes itself (the brief, the repository bundle, the connectors' file). Only what becomes a folder or branch name keeps a validator: task ids and member ids. `team bot add` with a catalog declaration whose `id:` looks like a key copies it with the id replaced by the file name (the id must equal it anyway).

*The index.* The receipt index is a cache. Its stamp and rows hold no source path (each source is named by a hash of its path) and no registered value: receipts are masked as they are read. It is rebuilt when a receipt, the stamp format or the secret store changes, and when the stamp's hash of the loaded mask set changes, and when a cached row holds a value the registered set now masks (a value rotated without a change the store's files show, e.g. in a `pass` backend). A rebuild removes the file first, with `secure_delete` on, so no old row stays in free pages. An index built before this rule is replaced on first use. When a run passed keys that are not in the store, `log` keeps the index in memory and removes the file; `team` also removes a bot's index when it collects the bot's results.

*What is refused.* `log add` refuses a signal, ref or cost that looks like a key. `team export` refuses a file whose contents hold a key or a registered value, binary files included (a silently changed setting would be worse than none), refuses every symbolic link in the exported tree, files and folders, because an archive keeps a link's target name, and refuses two files that map to one name. `team import` refuses unsafe members (links, devices, `..`), a bot declaration whose name looks like a key, collisions as above, and any destination that is or goes through a link in the team folder. Settings, `provision.sh` and connectors in an archive are never applied, only quarantined.

*Container runs.* The keys passed to a container run reach it as `NAME=value` lines on standard input, with `WOUF_MASK` (the values passed for that run, as JSON) among them, so `team` and `log` inside the container mask the passed values before any sink, as host runs do through the environment. Receipts imported from elsewhere are masked on their decoded field values (registered values and patterns), before they are serialized again.

*Limits (masking is defense in depth against accidents, not a guarantee; these are not findings).* Only the key patterns and the registered values are recognized, as they stand, in text and in binary files alike: a value that a bot reflows, splits across lines, encodes (base64, UTF-16) or compresses passes, and so does a value that is neither registered nor key-shaped. A registered multi-line value is held back whole in streamed output only up to the stream buffer (400 lines); a longer one may pass there. Names are masked per path component: a value that contains `/` in a path is not masked as one.

## 7. Cheap, traceable state

State lives in the event log; the store is its cache, board and decisions are its readable export.

- **The event log** (`team/events/<origin>.jsonl`, in git) is the truth: one append-only file per origin, each line a validated, masked event of at most 4096 bytes (`task.created`, `task.state`, `question.asked`, `decision.recorded`, `schedule.item`, `phase.state`, `flow.step`, `run.finished`, `merge.proposed`, …), written under a lock and fsynced. A torn tail stops the writers until it is repaired; malformed lines are skipped and counted (`log state check`). Run receipts (`team/logs/*.jsonl`) stay one line per run.
- **The cache** (`team/env/state.sqlite`, 0600, WAL, not in git) is the materialised state and the bus: tasks, questions, decisions, schedule, phases, flows, runs and merges, projected from the events. Its stamp hashes source sizes, mtimes and path hashes, the mask set and the projection format; a changed source rebuilds it after removing the file with secure deletion, a verified append-only extension applies only the new lines. Readers poll its data version and sequence (`log state wait`). It can be deleted any time. Passed run keys keep it in memory, and bots never receive it: staging excludes the host environment folder.
- **The projections** are what people read: `team/board.md`, `team/decisions.md` and `team/schedule.md` are written from the cache by every state command (`team task`, `team question`, `team decision`, `team schedule`, `team merge`), never edited by hand; a hand edit is detected and offered for import (`team state diff`, `team state import`), never silently overwritten. A session starts with `team context`, one short read of the cache; `team snapshot --json` and `team events --since` give the same state to tools.
- **The receipt store** (`team/receipts/<landed>.json`, in git) holds one signed change receipt per landed commit (`docs/RECEIPTS.md`): `team receipt make` signs the canonical body with `[federation] signing_key` (only its `.pub` is read; ssh-keygen opens the private key), checks the signature, and writes the file, the `receipt.signed` event (task, landed, reviewed and the sha256 of the file) and the note `refs/notes/wouf-receipts` on the landed commit, all with the same bytes. The same receipt again changes nothing; another receipt or another note on that commit is refused. `team receipt resign SHA` is the one replacement: signed_at kept, resigned_at set, every other byte equal, the current key; it replaces the file and the note (`git notes add -f`) and writes `receipt.resigned`. Pushing the notes ref is the lead's land step.
- **An older team moves in** with `team state import team/board.md --apply`: each well-formed row whose id the store does not know becomes a task (`task.created` and `task.state`), a broken row is refused, and text outside the table is never imported.

Knowledge is Markdown in `team/knowledge/` (plus optional `[knowledge] sources`); `team ask` and `log ask` search it with SQLite FTS5/BM25 and quote what they find, together with accepted lessons and decisions. No vectors or embeddings: structured events and receipts do not need them. `log status`, `task` and `find` return a few lines instead of whole files. A task id names folders and git branches, so one validator, the same block in `team` and `log`, checks it before any state is created: one git ref component (no `.` at the end, no `..`, no `.lock` at the end), no Windows device name (CON, PRN, AUX, NUL, COM1-9, LPT1-9, with or without an extension), no key, and no case twin of a task the team already has.

## 8. Portable teams

A team is its declarations and settings. `team export` writes them without secrets or data (data on request). `team import` lists first and, with `--apply`, adds only data on another computer without overwriting: bot declarations (known keys only, always `proposed`), team skills, knowledge, board, decisions, schedule and `tools.md`. With data, the archive also holds a versioned migration snapshot (`migration/v1/`: the event log, flows, goals, the lead's briefs and the practice files, refused when one holds a secret); import applies it only to a team without events or migration metadata, because a snapshot cannot be merged with another team's state, and the cache is rebuilt from the events. What never moves: the bots' storage (their notes and subscription logins), keys, the image or prefix, and settings. On the new computer the human copies the settings from the quarantine, activates the bots (`status: active`, `team bot create`), signs them in or stores their keys again; repository paths in flows and goals are still the old computer's. Everything else in the file, settings, `provision.sh`, connectors and whatever else it holds, is quarantined in `team/import/<archive name>/` for the human to read and copy over by hand: kept as it was, except that registered secrets and recognised secret patterns in it are masked, and nothing in it is applied. The listing names the files where something was masked, with a count and never the value. Receipts (`.jsonl`) also arrive with any recognized key masked, since they never passed this team's `log add`. Listing every setting that runs a command proved impossible to make complete, so import never applies one. As a second line, `[environment] image` and `user` are checked before every Dockerfile and container command, whatever the source: only a plain image reference and a plain user name or `uid[:gid]` pass. The image is rebuilt there from the settings the human chose and `team/provision.sh`.

## 9. Flows without a model in charge

`team flow` runs the steps the lead would otherwise run by hand, as a small state machine: a pure function decides the next step from the steps so far, and every step is an ordinary `team run` or `team gate`, so each leaves its receipt and can be read on its own. No model decides what comes next; that keeps the chain cheap, repeatable and testable. The pre-gate runs the team's own checks on the exact head in a sandbox without keys before any reviewer spends tokens, and a review counts only when it approves that head. Each gate run gets a fresh checkout, a fresh `HOME` and a fresh work folder that no earlier run could write (in container mode they are the new container's own; only the cache is on the gate storage), and git reads no inherited configuration and runs no inherited hook during checkout and test: `GIT_CONFIG_GLOBAL` naming an empty, writable file in that fresh `HOME` (`.gitconfig`), `GIT_CONFIG_NOSYSTEM=1`, no template, and `core.hooksPath` set to an empty read-only folder. A gate command that needs a global git setting sets it for itself (`git config --global` works); the file is new and empty in every run, so nothing it writes reaches the next. `WOUF_CACHE` is a disposable writable view of a trusted warm cache; for example, `CARGO_TARGET_DIR="$WOUF_CACHE/target" cargo test` keeps build output there. Task gates cannot promote their writes: Podman mounts the lower cache volume as `-v <store>:/bot/cache:O`, and removes the container and its upper layer after the run. Engines without Podman's overlay support (including Docker) run with an empty cache in the disposable container and report that they cannot isolate the warm cache; warming is unavailable there. Host mode copies regular files from the read-only snapshot `team/env/gate/.cache` into each gate's own cache, skipping links and special files; snapshots over 256 MiB produce an empty cache with a message. Only explicit `team gate TASK --repo REF --base REF --warm-cache` may write the lower layer (or replace the host snapshot after a successful run), and only when `git merge-base --is-ancestor HEAD refs/heads/main` succeeds for the resolved gate head. Branch heads outside main are refused before running. Warm only while no other gate is running: overlayfs does not support changing a mounted lower layer. `team flow` never warms the cache. Thus untrusted gate writes are discarded, and only commits reachable from main supply a later task's warm data. Gate machinery never executes cache files or follows cache links; a gate command may itself trust artifacts warmed from main. `team gate --fresh-cache` empties both the snapshot and container lower layer, alone or before a run. Gates pass no keys and use at most three engine calls: image inspection, an optional image build, and one streamed bundle/container run with automatic removal. The container runs its entire setup and gate under `timeout -k 1 <limit>` so a time limit terminates the gate inside the container, allowing automatic removal; the host watchdog allows ten additional seconds for that cleanup. Host mode is no sandbox: there a gate command runs as the human, so these measures keep runs from stepping on each other but do not contain one. A finding marked `[bug]` goes to a fresh bot with only the report, so the fix does not inherit the worker's reasoning. Usage limits are an expected state, not a failure: the unfinished work becomes a WIP commit, and the flow waits for the reset or moves the step to another CLI once. The state is a JSON file per task, so a flow that stops continues where it was.

*A change in packages* (T-0189, `teamlib/gate_series.py`). Each package of a change can pass its gate and review while the change is half built: on 2026-11-08/09 packages 3 and 4 of the five packages of T-0167 landed on main, and its migration and upgrade test came only with package 5. A brief that says `Series: NAME K/N` (NAME a task id, 1 <= K <= N <= 20) is therefore gated for completeness. On a base on main (`[gate] main`, default `main`; a base commit on that branch counts as main, and a repository without that branch is red), a package K < N is red: a series lands on a feature branch that starts with a commit of its own, then as one complete change. That change, `Series: NAME N/N`, is red unless its diff holds the migration `.agents/upgrade/<VERSION>.md` of the head's VERSION (VERSION unchanged: or the brief's `Migration: none REASON`) and an upgrade test `tests/test_upgrade_*.py`. After a green suite the gate runs that test itself on the head, in a sandbox run of its own (`gate_execute`, as the suite, so the suite cannot change its exit code), and appends its output to `gate.log`. A malformed or second Series line is red. `gate.json` keeps `series`, `migration` and `upgrade_test`; a brief without a Series line gates as before, and its `gate.json` has none of them. The gate checks that the migration and the test exist and that the test passes, not what they cover: that stays the review's (`skills/review-merge.md`).

The `catalog/` folder of optional skills and tools lies outside the pack and is never loaded; a team copies an entry into its own skills or tools to use it.

## 10. The lead's write boundary

The lead talks, briefs and dispatches; it does not change code (section 3). With `[guard] lead_mode = on` in `team/config.ini`, `.agents/bin/guard` holds the lead's own session to that when a tool is called, not at the next start. Lead mode is an allowlist for the lead's tool calls: the session may write only `[guard] lead_write` (globs relative to the project, or absolute or `~`-rooted, for example `team/briefs/**`, `docs/notes/**`, `outbox/**`) and `write_roots` (its memory folder, a scratchpad), and a refusal names the path or the command and says "brief a bot". A file tool's path (Write, Edit, MultiEdit, NotebookEdit, a patch, the path of a tool the guard does not know as a reading one) is resolved against the `cwd` of the hook payload (a relative path in a payload without one is refused: "cannot tell where this writes"), then `..` and symlinks (a file with another hard link is refused too). A shell line is allowed only when every simple command in it (split at `;`, `&&`, `||`, `|`, `( )` and `{ }`) matches a listed shape with only the listed options, from that working folder (or the guard's own without one): the readers (`cat`, `head`, `grep`, `ls` and the like), `sed -n` with a script of addresses and `p` or `=`, `sort` and `uniq` without an output file, `find` with a few tests, `cd ./DIR` (or `../DIR`, an absolute folder, `~` or `~/PATH`) inside the project or a write_root, `mkdir`, `cp` and `mv` into lead_write, git's reads, `git add` of existing lead_write files, `git commit -m` when every staged path is in lead_write, gh's reads, the pack's `team`, `log` and `federate`, a `[guard] lead_run` script that neither lead_write nor a write_root covers (as written or where it resolves), run with `bash PATH ...`, `. PATH` or `source PATH` (these two with no other word), and `NAME=VALUE` or `export NAME=VALUE` for a name of `[guard] lead_env` with `$(pass show ENTRY)` or a short literal that cannot name a path (below); a redirection writes only to `/dev/null` or a lead_write or write_roots path with `>` or `>>` (also `1>` and `1>>`); `2>&1` and `2>/dev/null` are the only other descriptor forms (`2>FILE`, `3>FILE`, `9>/dev/null`, `>&N`, `1>&2`, `>|`, `<>`, `&>`, `&>>` and the like are refused). `.agents/bin/guardlib_lead.py` lists the shapes and their options. A construct the guard does not parse (`eval`, `bash -c`, `sh -c` or another shell `guardlib_lead.py` lists (`SHELLS`) given an option or no script, also in a hook's argv such as `["bash", "-lc", LINE]`, a `$(...)` other than that one outside a lead_env value, a loop, a function, `xargs`, `exec`, a heredoc to a command not listed) refuses the line with "cannot tell where this writes", any other command or option with "not on the lead's list: brief a bot". Git is refused in a repository whose git folder, config or hooks folder lead_write or a write_root covers, and so is a shell write into a `.git` folder. Code files, the secret store, `.env` files and the files that would switch the mode off (`team/config.ini`, `team/guard-deny.txt`, `.agents/bin/guard*`, the CLIs' settings files) stay refused even inside lead_write. With `lead_mode = off`, the default, the guard does exactly what it did before.

A word the shell expands is taken only where its expansion cannot change what the guard checked. `uniq` (its OUTPUT operand) and `sed` (its SCRIPT, which could hold `w FILE`) refuse a glob (`*`, `?`, `[`), a brace expansion (`{a,b}`, `{1..3}`, also `{"a}",b}`), a `~` other than `~` and `~/PATH`, a `~` after the `=` of `NAME=` and `$"..."`: to the shell `uniq src/*` is `uniq src/a.txt src/b.txt`, which overwrites `src/b.txt` (review T-0188.r12). Every path the guard checks (a redirection's target, `cd`, `mkdir`, `cp`, `mv`, `git -C`, `git add`, the words of `git commit`, `bash`, `.` and `source`, a pack tool) refuses the same words, because bash leaves `~"/x"` as it is and drops the `$` of `$"../x"`. The readers, `find`, git's reads and gh have no operand that writes: theirs may expand after a fixed first character, which cannot make an option. bash ends a heredoc's body at its delimiter as written, without expanding it, so a delimiter with a `$`, a backtick or a part the shell computes (`<<E$X`, `<<"E$X"`, `<<$'EOF'`, `<<${X}`), like an unquoted body line that ends in `\`, which bash joins with the next one, refuses the line with "cannot tell where this writes" (review T-0188.r19). bash looks a relative `cd` folder that starts with neither `./` nor `../` up in `CDPATH` first, so such a `cd` refuses the line with "cannot tell where this writes" (`CDPATH` stays refused as a lead_env name), and a `cd` sets the working folder of the commands after it only where bash runs it in this shell for sure, with the known gaps below: at the start of the line or after `;` or `&&`, with no `||` before it in its and-or list, outside a pipeline, `( )` and `{ }`, and before `;` or a newline only when its folder exists and no `&&` stands before it (bash skips it when the command before fails); elsewhere every later path must hold in the old folders too (reviews T-0188.r20 and r21).

`[guard] lead_env` names the variables the lead may set with `NAME=VALUE` before a command or with `export NAME=VALUE`. The guard refuses the names of `ENV_RUNS` in `guardlib_lead.py` even when lead_env lists them: such a name is ignored, with one stderr line that names it, so as a prefix or an export it refuses the line with "not on the lead's list: brief a bot" (review T-0188.r11: with `lead_env = HOME`, `HOME=docs/notes git status` read a `.gitconfig` the lead had written there and ran its `core.fsmonitor` command). `ENV_RUNS` holds `HOME`, `PATH`, `IFS`, `ENV`, `SHELL`, `ZDOTDIR`, `VISUAL`, `POSIXLY_CORRECT`, `PWD`, `OLDPWD`, `TMPDIR`, `TMP`, `TEMP`, `EXECIGNORE`, `PS0` to `PS9` and `PROMPT_COMMAND`, every `OPENSSL_CONF*`, `LD_*`, `DYLD_*`, `GIT_*`, `PYTHON*`, `XDG_*`, `BASH*`, `PERL*`, `RUBY*`, `NODE_*`, `LESS*`, `TERMINFO*`, `PASSWORD_STORE_*` and `HIST*`, and every name that holds `CONFIG` or ends in `HOME`, `PATH`, `RC`, `PAGER`, `EDITOR`, `BROWSER`, `ASKPASS`, `OPT`, `OPTS` or `OPTIONS`. Every lead_env value must be a pass entry, exactly `$(pass show ENTRY)`, or a short literal that cannot name a path: after quote removal only letters, digits and `_ . : @ + , = -` (so no `/`), not `.` or `..`, not starting with `~` or `-`, and not the name of a file, folder or link in the folder the command runs in when the guard checks the line. Any other value refuses the line with "not on the lead's list: brief a bot" (so does `NAME+=VALUE`, and any substitution other than `$(pass show ENTRY)` in the value), so `SSL_CERT_FILE=docs/notes/cert.pem`, and `TZDIR=notes` where `./notes` exists, are refused even when lead_env lists the name (review T-0188-fix10.r3). Any other name is trusted as the owner listed it: the guard bounds its value, not what a program reads from it. `GH_TOKEN`, `WOUF_TEAM_DIR`, `SYNC_PACK_ON_LAND` and `PKG_MAIN`, the example in `config.ini`, are not in `ENV_RUNS`.

This is a tripwire on the lead's tool calls, and only where the host wires the guard in as the CLI's pre-tool hook; it is not a sandbox. The trusted scripts of lead_run and the pack's own tools run unseen: the guard does not look inside them. The host's restricted account or OS sandbox is the stronger boundary.

### Known gaps (0.2.0)

These crafted bypasses are recorded for 0.2.1.

- A `cd` with a redirection that fails is still taken as run.
- A `cd` through `..` after a folder that does not exist (or a file) is still taken as run.
- bash follows a folder symlink logically and the guard physically, so a `cd ..` after one can end elsewhere.

## What it is not

Not a sandbox technology, a workflow engine, or a hosted service. It organises the tools you already have.
