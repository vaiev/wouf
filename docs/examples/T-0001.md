# Worked example: T-0001 on Vaikor

This is the first task the WOUF team did on [Vaikor](https://github.com/vaiev/vaikor), a Rust project, on 2026-10-25. It is small on purpose: the interesting part is what the team did when the gate turned red for a reason that had nothing to do with the task.

The lead was a Claude Code session (Claude Opus 5.5), the worker Claude Code in a container, the reviewer Codex CLI in a container. The containers ran on a rented server through rootless Podman.

## The brief

The lead wrote this brief from a one-line idea of the owner and started `team flow T-0001`:

```text
Task: T-0001
Class: mechanical
Paths: scripts/tests/pre_gate_check.sh, scripts/ci-local.sh
Objective: Add a shell test for the argument checks of scripts/pre-gate.sh and run it from scripts/ci-local.sh.
Acceptance criteria:
- scripts/tests/pre_gate_check.sh exists, is executable, starts with the same copyright/SPDX header as
  scripts/tests/private_refs_check.sh, and passes `shellcheck -x`.
- It builds a throwaway git repository in a temp dir (removed on exit) and asserts: pre-gate.sh with no base
  exits 2; with a base that is not an ancestor of HEAD exits 2; with a base that is no commit exits 2.
  It never runs cargo.
- It prints one line per case and exits 0 only when all three pass.
- scripts/ci-local.sh runs it: one line in the private_refs function, nothing else changes there.
Out of scope: changing scripts/pre-gate.sh, any Rust code, CI workflows.
Constraints: bash, set -euo pipefail, no network, no new tools. Commits signed off with `git commit -s`.
```

`Class: mechanical` lets the flow start on the light model tier.

## What happened

| Time (UTC) | Step | Result |
|---|---|---|
| 04:13 | worker (light) | one commit, `ready-for-review` |
| 04:13–04:16 | gate (`scripts/pre-gate.sh` in a container) | red: the Rust `test` step failed |
| 04:16–04:21 | worker (strong, after the red gate) | `blocked`, with two questions |
| 04:30 | lead | fixed the team image |
| 04:33 | worker (light) | verified the commit, `shellcheck -x` now clean |
| 04:43–04:51 | gate (retry) | green |
| 04:51–04:52 | review (Codex) | `APPROVE 1a2b3c4` on the exact head |

The worker did not touch Rust code to make the gate pass. It reported what it could and could not verify:

```text
WOUF Worker · T-0001 · blocked
- `shellcheck -x` → NOT verified: shellcheck is not installed in this sandbox
- pre-gate green → NOT achieved: the `test` step fails (runtime/vaikor-tui/tests/...), out of my scope
Questions:
- I need a decision on the red `test` step: it is in Rust tests or the toolchain, both out of my scope.
  Should it be fixed in a separate task, or should the gate run with a toolchain where those tests compile?
- I need shellcheck in the sandbox, or someone else to run `shellcheck -x`.
Flags: the red looks pre-existing and unrelated to T-0001, but I did not run the gate at the base to prove it.
```

The cause was the team image, not the task: the container linked the Rust toolchain through a wrapper whose shell dropped the `CARGO_BIN_EXE_*` variables the integration tests rely on, and shellcheck was missing. The lead linked the toolchain directly, added shellcheck to the image recipe (`team/provision.sh`) and retried the gate. The review then checked the paths, the sign-off, the header, the three exit codes, the cleanup and the one-line change, and approved the exact commit.

The lead merged the branch and pushed it after the owner's OK.

## What it shows

- **The gate is the referee.** The worker said "ready" twice; only the gate and the review decide.
- **Blocked is a good answer.** The worker stopped at its scope and asked, instead of changing Rust tests to turn the gate green.
- **The lead owns the environment.** Image, toolchain and tools are the lead's job; the fix went into the team's image recipe, so every later task has it.
- **Approval is tied to a commit.** `APPROVE 1a2b3c4` is void if the branch moves. (Commit ids in this example are illustrative.)

Total wall time 39 minutes, most of it the Rust build in the gate.
